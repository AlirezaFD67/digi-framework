# راهنمای استفاده از داکیومنت‌های Monorepo با AI همکار

## معرفی
این فایل راهنمای کاملی برای ارتباط با AI همکار (من) در فرایند توسعه **Monorepo** مبتنی بر Next.js، Turborepo و pnpm است. 

### ویژگی‌های Monorepo ما:
- 🏗️ **Turborepo**: مدیریت build و task orchestration
- 📦 **pnpm workspaces**: مدیریت بسته‌ها و dependency sharing
- 🎯 **@workspace/framework**: API management متمرکز
- 🎨 **@workspace/custom-ui**: کامپوننت‌های گلوبال
- 🧩 **@workspace/ui**: کامپوننت‌های shadcn/ui پایه
- 🚀 **Multiple Apps**: admin-panel, digimoragheb, docs

داکیومنت‌های موجود (مثل `before_task.markdown`, `ARCHITECTURE.markdown`) برای استانداردسازی توسعه در این ساختار پیچیده طراحی شده‌اند.

اگر تازه وارد شده‌اید، از اینجا شروع کنید!

---

## چرا این داکیومنت‌ها مهم هستند؟
- **استانداردسازی در Monorepo**: همه تسک‌ها بر اساس ساختار Monorepo و workspace packages انجام می‌شوند
- **جلوگیری از تکرار کد**: مشخص است چه زمانی باید کامپوننت در `custom-ui`، چه زمان در اپلیکیشن خاص ایجاد شود
- **مدیریت صحیح API**: تمام API logic در `@workspace/framework` متمرکز است
- **کاهش خطا**: چک‌لیست‌ها تضمین می‌کنند هیچ مرحله‌ای فراموش نشود
- **همکاری با AI**: من بر اساس این داکیومنت‌ها کد می‌زنم، تست می‌نویسم، و پیشنهاد می‌دهم
- **یکپارچگی**: همه چیز در `prompts/task/` سازماندهی شده است

---

## گام‌به‌گام: چطور از داکیومنت‌ها استفاده کنی؟
فرایند ساده‌ست و بر اساس مراحل زیر پیش می‌ره:

### ۱. قبل از شروع تسک
- فایل `OVERVIEW.markdown` رو بخون تا با همه داکیومنت‌ها آشنا بشی.
- فایل `before_task.markdown` رو مطالعه کن و چک‌لیست‌ها رو چک کن (مثل بررسی نسخه‌ها، ساخت برنچ).
- **داکیومنت رو به AI بده**: محتوای فایل `before_task.markdown` رو کپی کن و بفرست (یا فایل رو attach کن).
- **تأیید بگیر**: من فرایند رو بررسی می‌کنم و می‌گم آماده‌ایم یا نه. اگر OK باشه، شروع کد می‌کنیم.

### ۲. در حین تسک (اگر نیاز باشه)
- اگر سؤال داری، به داکیومنت‌های مرتبط مراجعه کن (مثل `CODING_GUIDELINES.markdown` برای نام‌گذاری).
- اگر فایل‌های اضافی نیاز باشه (مثل کدهای موجود)، بگو تا من بپرسم.

### ۳. بعد از پایان تسک
- فایل `after_task.markdown` رو مطالعه کن و چک‌لیست‌ها رو انجام بده (مثل مستندسازی، تست‌نویسی، کامیت).
- **داکیومنت رو به AI بده**: محتوای فایل `after_task.markdown` رو بفرست.
- **کمیت بده**: من عنوان کامیت استاندارد پیشنهاد می‌کنم (به انگلیسی، مثل `Feat: Add user management`).
- **اگر آپدیت باشه**: از `before_update.markdown` و `after_update.markdown` استفاده کن.

### ۴. اگر تسک آپدیت باشه
- فایل `before_update.markdown` رو بده برای شروع.
- فایل `after_update.markdown` رو بده برای پایان.

## لیست داکیومنت‌ها و نقش هر کدام
اینجا لیست کاملی از داکیومنت‌ها و زمان استفاده‌شون:

| داکیومنت | نقش | کی بده به AI؟ |
|----------|-----|---------------|
| `OVERVIEW.markdown` | معرفی همه داکیومنت‌ها و FAQ | همیشه اول بخون (نیازی به دادن نیست) |
| `before_task.markdown` | چک‌لیست قبل از تسک | قبل از شروع هر تسک |
| `after_task.markdown` | چک‌لیست بعد از تسک | بعد از پایان هر تسک |
| `before_update.markdown` | چک‌لیست قبل از آپدیت تسک | قبل از آپدیت تسک |
| `after_update.markdown` | چک‌لیست بعد از آپدیت تسک | بعد از آپدیت تسک |
| `ARCHITECTURE.markdown` | ساختار پروژه و فولدرها | اگر نیاز به توضیح معماری باشه |
| `CODING_GUIDELINES.markdown` | نام‌گذاری، محل فایل‌ها، بهترین روش‌ها | برای قوانین کدنویسی |
| `COMPONENT_GUIDELINES.markdown` | لیست کامپوننت‌های استاندارد | برای استفاده از کامپوننت‌ها |
| `API_GUIDELINES.markdown` | نحوه اتصال به API و React Query | برای APIها |
| `API_DOCUMENTATION.markdown` | قالب مستندسازی endpointها | برای مستندسازی API |
| `AUTH_GUIDELINES.markdown` | احراز هویت و کنترل دسترسی | برای لاگین/رول‌ها |
| `GENERAL_GUIDELINES.markdown` | نصب پکیج‌ها، خطاها، لاگ‌گیری | برای تنظیمات عمومی |
| `PERFORMANCE_GUIDELINES.markdown` | بهینه‌سازی عملکرد | برای سرعت و لود |
| `SEO_GUIDELINES.markdown` | بهینه‌سازی SEO | برای موتورهای جستجو |
| `TESTING_GUIDELINES.markdown` | نحوه تست‌نویسی | برای تست‌ها |
| `TASK_DOCUMENTATION_GUIDELINES.markdown` | قالب مستندسازی تسک‌ها | برای مستندسازی |

## نکات مهم
- **فایل‌های اضافی**: معمولاً داکیومنت‌ها کافی هستن، اما اگر تسک نیاز به کد موجود داشته باشه (مثل فایل‌های `components/` یا `types/`)، بگو تا من بپرسم.
- **تأیید کاربر**: همیشه قبل از کامیت یا push، تأیید تو (صاحب پروژه) رو می‌گیرم.
- **زبان**: ارتباط به فارسی باشه، اما کامیت‌ها به انگلیسی.
- **اگر گیجی**: اگر چیزی واضح نبود، بپرس – من توضیح می‌دم.
- **به‌روزرسانی داکیومنت‌ها**: اگر تغییری نیاز باشه، بر اساس `after_update.markdown` عمل کنیم.

---

## مثال سناریو
فرض کن می‌خوای کامپوننت جدید "UserForm" اضافه کنی:

1. `before_task.markdown` رو مطالعه کن و چک‌لیست‌ها رو چک کن.
2. فایل `before_task.markdown` رو به AI بده.
3. AI فرایند رو تأیید می‌کنه و شروع به کد زدن می‌کنه (بر اساس `CODING_GUIDELINES.markdown` و `COMPONENT_GUIDELINES.markdown`).
4. بعد از کد، `after_task.markdown` رو بده.
5. AI تست می‌نویسه، کامیت پیشنهاد می‌کنه، و منتظر تأیید تو می‌مونه.
